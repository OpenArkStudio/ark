# 启动与停机交付状态

框架负责有序启动与进程资源释放。应用或运维在进程停止前完成公告、关闭业务入口、踢人和保存；框架不提供业务准入或自然业务排空阶段。

## 启动保持失败即退出

已声明提供方决定四个启动阶段的提供方优先顺序。依赖缺失或成环时在钩子前失败；未声明依赖的模块互相独立。就绪节点按注册键排序，不按清单顺序。安装或未完成的钩子可能已经获取资源，拓扑不能代替资源获取补偿。

启动失败时，启动器报告阶段／所有者，只调用获取资源前显式注册的独立清理，然后通过 `_Exit`（Windows 另调用 `TerminateProcess`）以 `1` 退出。预分配注册表最多容纳 16 个 owner，按注册逆序清理，在不安全或失败时提前停止。不执行正常停机钩子、对象／静态析构、DSO 卸载或同进程重试。Utility Timer 的无回调时间轮清理不覆盖仍持有的业务回调或共享 IO。见[启动失败清理](startup-failure-cleanup_CN.md)。

## 进程资源停机

<Steps>

<Step title="停止前完成业务操作">

应用或运维先完成停服公告、关闭业务入口、踢人和保存，再请求停止进程。

</Step>

<Step title="请求资源取消">

`stop()` 进入 `stopping`，对任务组调用 `close()` 关闭顶层任务准入并请求取消，不强制销毁挂起的协程帧。

</Step>

<Step title="驱动安全完成">

继续 `manager.update()`，派发服务／桥接完成并统一轮询一次共享执行器。等待任务实际完成、活跃栈返回，以及全部模块的 `ready_to_shut()` 就绪。false 表示继续等待；异常进入 `failed`。

</Step>

<Step title="先释放消费者再释放提供方">

按声明依赖执行两次反向遍历：先在全部模块对象存活时执行所有 `pre_shut()`，关闭并等待原生回调源退出；再逐个执行 `shut()` 并销毁拥有的对象，消费者先于提供方。首个 false 或异常停止后续清理。

</Step>

<Step title="最后关闭动态库">

全部模块释放后才注销插件。模块析构、回调／捕获对象析构和插件出口期间保留全部 DSO，最后关闭原生动态库。成功进入 `stopped`，重复 stop 成功。

</Step>

</Steps>

取消是协作式请求，可能无法中断等待的操作，也不能撤销远端写入。任务归零不证明回调／原生线程安全；模块必须保留所有者和代码直到原生工作就绪。依赖声明须覆盖真实借用关系；Map／Kernel 的运行时环未声明为依赖环。外部所有者与未声明依赖仍由应用负责。独立所有者保留 `task_group::poll()`；管理器任务由管理器更新驱动。HTTP 续接不再依赖轮询阶段授权。

提供方对象在消费者 `shut()`／析构期间仍存活，但其原生资源可能已由前一轮 `pre_shut()` 关闭。此时仅可按接口约定释放借用或注销元数据，不可依赖提供方继续接受数据库写入、网络发送或业务保存；这些动作须在运行期、停止进程前完成。

### 原生资源边界

| 所有者 | 资源回收 |
| --- | --- |
| 受管任务 | `close()` 请求取消；服务完成与共享执行器轮询使帧实际结束 |
| MySQL／Redis | 就绪检查观察服务／桥接静止；`pre_shut()` 关闭准入，通过原生 `close_and_wait()` 回收池；`shut()` 确认原生退出后清空连接 |
| Net HTTP 客户端 | 就绪检查等待原生结果、排队交付、活跃回调及捕获释放；`pre_shut()` 关闭／取消运行时，不区分业务根与续接 |
| 路由 HTTP 服务端 | 就绪检查原子封闭原生路由派发，等待活跃路由／响应发送持有状态结束；`pre_shut()` 停止并等待服务端退出，释放端点；不再按管理器状态返回 HTTP 503 |
| Utility 调度器 | 就绪检查请求资源关闭，丢弃队列中的定时任务并关闭后续调度，等待已派发回调和捕获对象回收；`pre_shut()` 等待已结束的工作线程退出，不承担业务准入 |
| Net 服务 | 所有者清理关闭端点并释放借用回调的捕获对象，再销毁消费者／提供方；普通协议回调保持原注册行为 |

原生关闭或 `dlclose`／`FreeLibrary` 成功不证明操作系统已物理移除库映像，也不证明任意热更新安全。

### 可选资源期限与保留

`--shutdown_timeout_ms` 默认 `0`，表示无限等待。正数通过 `stop_until()` 设置单调时钟截止时间，最早传入的期限在后续调用中持续生效。

| 状态 | 行为 |
| --- | --- |
| `running` | 正常执行 |
| `stopping` | 继续 owner 更新，等待任务、活跃栈与原生资源安全 |
| `timed_out` | 可选期限在清理前到期；保留资源，允许 owner 更新，不恢复清理 |
| `cleanup_timed_out` | 清理开始后超时；保留剩余资源，不继续更新或清理 |
| `failed` | 就绪／清理／原生关闭失败；保留剩余资源，不重试后续清理 |
| `stopped` | 钩子、对象析构、插件出口与原生关闭成功 |

期限检查发生在就绪／清理返回边界与清理前，不能抢占阻塞的钩子、原生 join 或关闭，也不能撤销已完成工作。启动器输出一次 `shutdown:` 上下文。owner 更新失败后，即使后续更新恢复，启动器仍保持资源保留。超时／失败不允许销毁待完成帧或按成功退出。

## 迁移与剩余边界

**BREAKING CHANGE：** 移除 `module::stop_accepting()` 与 Net 的 `reg_external_root_callback()` 助手。删除模块覆写，将助手注册改为普通协议回调；应用需要的业务入口控制在停止进程前自行完成。移除 HTTP 请求续接特例与按管理器状态返回 HTTP 503 的准入。启动器、全部官方／业务插件及受影响消费者须使用兼容头文件和编译器设置一起重建，不混用旧二进制。查找键和线协议不变。

启动失败即退出及已注册的启动清理合同不变。共享 IO 启动失败清理、未声明的跨插件回调生命周期、Registry 和热更新仍是独立工作。依赖顺序不证明生产容量或通用卸载安全。

## 验证范围

永久目标包括 Core 任务／依赖／清理测试、`check-app-business-runtime`、`check-app-shutdown-deadlines`、`check-native-unload` 与受影响的官方插件套件。目标存在不等于本修订已通过；执行时须报告命令、源码修订与实际结果。测试的自有子进程观察期限用于终止保留进程，不代表框架成功停机。

[数据库服务报告](../reports/database-services_CN.md) 保留已记录修订的历史真实服务证据，包括当时的自然排空；这些结果不验收当前取消式进程停机。本地原生测试、托管 CI、已发布文档和生产容量是不同结论。
